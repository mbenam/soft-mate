# M8 Probe Authoring Spec — Making Generated `.m8s` Files Valid On Hardware

Everything about *what a probe file contains* and *how its audio is compared to the
clone's render*. Companion to `M8_DRIVER_SPEC.md`, which covers everything that
talks to the device over serial.

**The split is "does this open a serial port," not "which goal does this serve."**
Nothing here touches `m8_nav`, `M8Device`, or the framebuffer. Every step is
verified by offline byte diffs and WAV analysis. Files touched:
`src/tools/main_makeprobe.cpp`, `src/tools/main_capture.cpp`,
`src/tools/main_render.cpp`, `third_party/m8-files-cxx/`.

> **Status.** Not started. This spec blocks the audio-parity goal outright: probes
> generated by `m8_makeprobe` currently play near-silent or silent on real
> hardware, so no capture-vs-render comparison made with them means anything.
> `M8_DRIVER_SPEC.md` Track B builds the plumbing; this spec makes the payload
> valid. **Do them in that order or in parallel, but do not report a parity result
> until P0-P4 are done.**

---

## The problem, and its documented history

This is the **third** instance of one bug class. Two were found and fixed:

- `song.midi_settings` written uninitialized — "uninitialised-memory MIDI routing ⇒
  silent probes on hardware" (`ARCHITECTURE.md`, `M8_HARDWARE_TEST_SPEC.md`). Fixed
  2026-07-17.
- fmsynth/hypersynth silent-by-default (`M8_APP_AUTOMATION_SPEC.md` §T4). Fixed.

One is still open:

- **Sampler probes are ~125× quieter** than a natively-authored instrument with
  identical nominal settings: capture peak 82 vs 10302 out of 32768
  (`M8_DEVICE_CONTROL_SPEC.md` §"Out of scope for this tier"). Root cause unknown as
  of 2026-07-18. Ruled out: the AHD→VOLUME mod envelope (replicating it on the
  native instrument had zero effect on its volume).

All three are the same shape: **a field the M8 reads that our writer gets wrong** —
wrong value, wrong offset, or never written.

### The obvious amplitude suspects are clean — do not re-check them

Confirmed by reading `src/tools/main_makeprobe.cpp`:

| Field | Value | Line |
|---|---|---|
| `volume` (CLI default) | `0xE0` | 470 |
| `sp.volume` | from `volume` | 164 |
| `sp.mixer_dry` | `0xC0` | 179 |
| `sp.mixer_pan` | `0x80` | 178 |
| `mixer_settings.master_volume` | `0xE0` | 310 |
| sampler branch calls `makeSynthParams()` | yes | 237 |

The sampler branch is **not** missing the mixer setup — it shares
`makeSynthParams()` with every other instrument type. Nothing nominally quiet.
Spending time here is a dead end that has already been walked.

### Why it has stayed "root cause unknown"

`verifyRoundTrip` (`main_makeprobe.cpp:385`) reads the generated file back with
**your own reader**, which mirrors **your own writer**. A field written at the wrong
offset, or one the M8 needs that you never write, round-trips perfectly and is still
garbage to the device. It also only checks instrument type, shape/timbre/color, and
`sample_path` — never `volume`, never the mixer fields, never the mod envelope.

**Self-consistency is not correctness.** This check is structurally incapable of
catching this bug class, which is exactly how the `midi_settings` bug survived to
hardware. Passing it means nothing here.

The fix is a **cross-oracle** comparison: something the device produced, versus
something we produced, for nominally identical settings.

## Reading this spec if you are an implementing agent

Same discipline as `M8_DRIVER_SPEC.md`:

1. **One commit per step**, message prefixed with the step id.
2. **Tick the checklist in this file** in the same commit. It is the progress record,
   not your memory.
3. **Re-read a step's section before starting it.** Don't work from recollection.
4. **Stop if a Verify fails.** Report; don't work around.
5. **Steps marked `[SD]` need physical access to the M8's SD card.** The M8 does not
   expose its card over USB. If you can't get the card, stop at that step and say so
   — do not substitute a guess.
6. **Do not "fix" the fields in the table above.** They're clean.

### Invariants

1. **No absolute-amplitude claim is valid until P0 passes.** Any "N× quieter" figure
   measured before the recording level is pinned is suspect.
2. **`verifyRoundTrip` is not evidence of correctness.** Never cite it as proof a
   probe is valid.
3. **The device-authored `.m8s` files are the ground truth.** When our writer and a
   device file disagree, our writer is wrong.
4. **Do not chase MIDI 24-27 silence as a defect.** See P8.

### Progress checklist

```
[x] P0   Pin the capture measurement baseline
[ ] P1   [SD] Capture device-authored golden .m8s per instrument type
[x] P2   Byte-diff harness: generated vs device golden
[ ] P3   Fix what the diff reveals
[ ] P4   Replace verifyRoundTrip with cross-oracle validation
[ ] P5   Resolve the AHD envelope contradiction
[ ] P6   Normalize the capture-vs-render comparison
[ ] P7   Re-measure the sampler amplitude bug
[ ] P8   Note-range sanity + doc corrections
```

### Step P0 — Pin the capture measurement baseline

**Files:** `docs/tools/hw_findings.md` (append `## P0`), possibly
`src/tools/main_capture.cpp`

**Why this is first.** `M8_HARDWARE_TEST_SPEC.md` records an open device-side
finding: since a power cycle, **USB captures read ~100× too low even for a
full-scale sample confirmed loaded on-device**, and the M8's `OUTPUT VOL` does not
affect the USB tap — the suspected cause is the host's **Windows recording level for
the M8 input, which resets on USB re-enumeration**.

The open amplitude bug is ~125×. The recording-level issue is ~100×. Those are the
same order of magnitude. They may well be independent — the 125× finding was
recorded as a controlled A/B (same sample, same nominal AMP, one built via the
device's own UI) which would cancel a shared attenuation — but **no absolute
amplitude number from this rig is trustworthy until this is pinned.** Chasing the
125× before pinning the baseline risks debugging a measurement artifact.

**Change.**

1. Determine and write down the correct Windows recording level for the M8 input,
   and how to verify it. Record the exact steps.
2. Capture a known full-scale reference: play a full-scale sample confirmed loaded
   on-device, and record the peak. Do this **twice with a USB re-enumeration in
   between** (unplug/replug) to establish whether the level actually resets.
3. Add a `--check-level` mode (or a documented startup assertion) to `m8_capture`
   that records the peak of a known reference and warns loudly if it is below an
   expected floor.

Record in `hw_findings.md`: the correct level, whether re-enumeration resets it, the
reference peak before and after, and the floor `--check-level` should use.

**Verify.** Two captures of the same reference, with a re-enumeration between them,
produce peaks within a few percent of each other — or, if they don't, the difference
is written down and `--check-level` catches it.

### Step P1 `[SD]` — Capture device-authored golden `.m8s` files

**Files:** create `tests/fixtures/device_golden/` and commit the files there; append
`## P1` to `docs/tools/hw_findings.md`

**Change.** For each instrument type `m8_makeprobe` supports (macrosynth, sampler,
wavsynth, fmsynth, hypersynth), author the equivalent instrument **on the device
through its own UI**, save it as a project, then pull the SD card and copy the
`.m8s` into `tests/fixtures/device_golden/`.

"Equivalent" means: same instrument type, same sample where applicable, same
nominally-set parameters `m8_makeprobe` sets — `volume 0xE0`, the same filter
settings, one phrase with one note at step 0, one chain, one song row, and the same
AHD→VOLUME mod (`dest=1, amount=0xFF, attack=0x01, hold=0x80, decay=0x80`).

For each file record in `hw_findings.md`: which settings you set by hand, which you
left at device defaults, the firmware version, and — critically — **whether the file
sounds correct when reloaded on the device.** A golden that doesn't itself play is
not a golden.

**Why.** This is the ground truth the round-trip check can never be. Two files with
nominally identical settings, one audible and one not: the difference between them
*is* the bug.

**Guardrail.** Author these by hand on the device, not with any of our tools. The
whole point is an oracle we did not write. Do not "save time" by loading a generated
probe and re-saving it — that launders our bytes through the device and destroys the
comparison.

**Verify.** Each committed golden, reloaded on the device, plays audibly. Record the
peak for each.

### Step P2 — Byte-diff harness

**Files:** create `tools/m8s_diff.py` (or a small `m8_filediff` target)

**Change.** A harness that, for a given instrument type:

1. Runs `m8_makeprobe` with settings matching the corresponding golden.
2. Byte-diffs the generated file against `tests/fixtures/device_golden/<type>.m8s`.
3. Reports every differing byte range as: offset, length, generated bytes, golden
   bytes — and, where the m8-files field map can name it, the field the offset falls
   in.

Report offsets in both decimal and hex. Group contiguous runs.

**Why.** This is the experiment that closes a bug open since July. It is mechanical,
it needs no hardware once P1's goldens are committed, and it converts "root cause
unknown" into "bytes at offset N differ."

**Guardrail — expect benign differences and enumerate them first.** Project name,
timestamps, and any device-written metadata will differ and are not bugs. Run the
diff once, classify each difference as benign or suspicious, and write the benign
list into the harness as an ignore set **with a comment naming why each is benign**.
An unfiltered diff that reports 40 differences teaches you nothing; a filtered one
that reports 3 is the answer.

**Verify.** The harness runs offline, produces a diff for at least the sampler type,
and its ignore set is documented.

### Step P3 — Fix what the diff reveals

**Files:** `src/tools/main_makeprobe.cpp` and/or `third_party/m8-files-cxx/`

**Change.** Depends on P2's output. The two shapes to expect:

- **A field with the wrong value.** Fix in `main_makeprobe.cpp`.
- **A field at the wrong offset, or an unwritten region.** Fix in the m8-files C++
  port's writer. This is the more likely and more serious case — it means the
  writer's layout disagrees with the M8's format, and *every* generated file is
  affected, not just probes.

**Guardrail.** If the fix lands in `third_party/m8-files-cxx/`, it is a fix to a port
of the m8-files Rust library. Check whether the upstream Rust library has the field
right — if it does, the port introduced the error and the diff against upstream
tells you where. Note in the commit whether upstream agrees.

**Guardrail.** After any writer fix, **re-run P2 for every instrument type**, not
just the one you were chasing. An offset error usually shifts more than one field.

**Verify.** P2's diff for the fixed type contains only entries from the documented
ignore set. Then, `[SD]`: put the regenerated probe on the card, load it, and confirm
it plays at a peak comparable to the golden's.

### Step P4 — Replace `verifyRoundTrip` with cross-oracle validation

**Files:** `src/tools/main_makeprobe.cpp`

**Change.** Keep `verifyRoundTrip` (it catches writer/reader crashes and gross type
errors) but demote it: rename its output to say what it actually proves, e.g.
`self-consistency OK (does NOT prove hardware validity)`.

Add a real check: `--verify-against <golden.m8s>` that runs the P2 byte comparison
inline and fails the build of a probe whose bytes diverge outside the ignore set.

Extend `verifyRoundTrip`'s field coverage while you're there — it currently checks
instrument type, shape/timbre/color, and `sample_path`. Add `volume`, the four mixer
sends, `mixer_pan`, and mod slot 0's `dest`/`amount`/`attack`/`hold`/`decay`. Those
are the amplitude-relevant fields and none of them are checked today.

**Why.** The failure mode that produced three silent-probe bugs is "our tools agree
with each other and are wrong." A check against an artifact we didn't write is the
only structural defence. Leaving the misleading `round-trip OK` message in place
after knowing this is how the next instance happens.

**Verify.** `m8_makeprobe --type sampler ... --verify-against tests/fixtures/device_golden/sampler.m8s`
exits 0 after P3, and exits nonzero if you deliberately perturb one field.

### Step P5 — Resolve the AHD envelope contradiction

**Files:** `src/tools/main_makeprobe.cpp`, `docs/` as needed

**Change.** Two documents disagree about the same envelope:

- `main_makeprobe.cpp:184-188` claims `hold=0x80`/`decay=0x80` gives ~2.67s at full
  volume then ~2.67s decay at 120 BPM — "ample for the >= 1.5s analysis window."
- `M8_HARDWARE_TEST_SPEC.md` states "parity probes need a **sustaining** amp — the
  current AHD→VOLUME mod decays to zero, giving a **~0.5 s blip**, not a steady tone
  to analyse."

Both cannot be true. Determine which by measuring: capture a probe and plot the
amplitude envelope over the whole capture window.

If it is a blip, the fix is a genuinely sustaining amp for parity probes — either a
mod configuration that holds, or no VOLUME mod at all with base `volume` carrying
the level.

**Why this matters for your reported symptom.** If the real behaviour is a ~0.5s
blip, then where the capture window lands relative to note-on determines the measured
peak. That produces **both** reported symptoms — "very low sound" and "no sound at
all" — from the same probe file, with no file bug involved. Resolve this before
concluding anything from P7's numbers.

**Verify.** A plotted or tabulated amplitude envelope over the capture window,
committed to `hw_findings.md` under `## P5`, plus the corrected comment in
`main_makeprobe.cpp`.

### Step P6 — Normalize the capture-vs-render comparison

**Files:** `src/tools/main_analyze.cpp` and/or `src/tools/main_spectrum.cpp`

**Change.** Make the comparison **peak-normalized and spectral**, not
absolute-amplitude:

1. Normalize both the hardware capture and the clone render to the same peak before
   comparing.
2. Compare spectra (the existing `m8_spectrum` / kissfft path) and envelope shape,
   not raw sample amplitude.
3. Report the applied normalization gain for each side. A large asymmetry in that
   gain is itself the signal that something is wrong with levels — surface it rather
   than hiding it inside the normalization.

**Why.** Given P0's finding that the host recording level is not reliably stable
across USB re-enumeration, absolute amplitude comparison between hardware and clone
is not a valid measurement. Peak normalization makes the comparison about *timbre and
envelope*, which is what the parity gate actually cares about, and which is robust to
level drift.

**Guardrail.** Do not normalize away information you need. If a probe is silent,
normalizing amplifies noise into something that looks like signal. Gate normalization
on a minimum pre-normalization peak and fail loudly below it.

**Verify.** The same probe captured twice at deliberately different recording levels
produces the same spectral comparison result.

### Step P7 — Re-measure the sampler amplitude bug

**Files:** append `## P7` to `docs/tools/hw_findings.md`

**Change.** With P0 (baseline pinned), P3 (writer fixed), and P5 (envelope resolved)
done, re-run the original comparison: generated sampler probe vs device-authored
golden, same sample, same nominal settings.

Record: peak for each, the ratio, and whether the ratio is now ~1. If a gap remains,
the P2 diff should now be the tool that explains it — re-run it and report which
fields still differ.

**Why.** This closes the loop on the bug that blocks the whole audio-parity goal, and
it does so with each confound eliminated in a known order, so a remaining gap is
informative rather than mysterious.

### Step P8 — Note-range sanity and doc corrections

**Files:** `M8_DEVICE_CONTROL_SPEC.md`, `M8_DRIVER_BUGS.md`, `docs/`

**Change.**

1. **Reclassify the low-note finding.** MIDI 24-27 (C-1 through D#-1) producing zero
   audio is recorded in two places as a "new, real finding" implying a defect. A
   sample repitched roughly three octaves down is plausibly just inaudible or below
   the output's usable range. Reclassify as "expected, not a defect — do not use
   notes below ~MIDI 36 for parity probes" unless a test at a sane note proves
   otherwise. This closes an open item that has been blocking Recipe 3 for no good
   reason.
2. **Update `M8_DRIVER_BUGS.md`** with the P3 root cause once found, and mark the
   ~125× entry resolved or re-scoped.
3. **Note the structural lesson** in `M8_HARDWARE_TEST_SPEC.md` beside the
   `verifyRoundTrip` description: a self-consistent reader/writer pair cannot
   validate a file format, and this bug class has now cost three separate
   investigations.

**Why.** Two of the four items in the open-findings list are probably not bugs, and
they've been treated as blockers. Clearing them is as valuable as fixing the real one.

## Open question this spec does not answer

The `third_party/m8-files-cxx` submodule was not available for inspection when this
spec was written, so **the writer's field layout has not been checked against the
M8's actual format.** P2 is designed to find out empirically rather than by reading
the port, because the empirical answer is the one that matters — but if P2's diff
shows offset-shifted fields, expect P3 to be a real piece of work in the port, not a
one-line value change.

Relatedly: whether the port's `MidiMapping` support is complete enough to author
CC→parameter mappings into a probe (which would let you set parameters over MIDI with
no UI navigation at all) is unverified. `main_makeprobe.cpp:321` resizes
`song.midi_mappings`, so the struct exists; whether the writer round-trips populated
mappings is unknown. Worth checking after P3, since it would make a large part of the
device-side parameter-editing problem disappear.
