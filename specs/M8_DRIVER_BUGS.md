# M8 Driver — Global Bug List

A single index of every real, hardware-confirmed bug found while building and hardening the
serial driver (`src/tools/m8/`), across all sessions. This is an index, not a duplicate — each
entry links to the fuller writeup in `M8_DEVICE_CONTROL_SPEC.md` where the hardware evidence,
symptom, and exact fix live. Status values: **FIXED** (in the codebase now), **REVERTED** (a fix
was built, hardware-confirmed unreliable, and deliberately removed rather than shipped),
**DATA** (not a logic bug — a field map had wrong/nonexistent coordinates, corrected), **OPEN**
(found, not fixed).

Numbering is chronological across sessions, not by severity.

---

## Driver bugs (in scope)

| # | Component | Status | Summary |
|---|---|---|---|
| 1 | `ScreenModel.h` — `findScreenForField` | FIXED | Type-blind for the Instrument screen: could only resolve field names against the Sampler map, so MacroSynth-only fields (SHAPE/TIMBRE/COLOR/REDUX) resolved to `Screen::UNKNOWN` before `moveCursorTo` ever got a chance to use the type-aware lookup. |
| 2 | `ScreenModel.h` — `identifyScreen` | FIXED | `stripDigits` only stripped trailing *decimal* digits, but phrase/chain/table IDs are hex (00-FF) and can end in a letter — `"PHRASE FC"` never matched `"PHRASE"`, so `gotoScreen` returned `UNKNOWN` for roughly half of all possible IDs. |
| 3 | `Primitives.cpp` — `moveCursorToGrid` | FIXED | Grid-screen cursor detection trusted a static, non-cursor `<` glyph over the real accent-cyan cursor color on PHRASE/TABLE, and a naive color scan (no row floor) could pick up the column-header label instead of the real cursor. |
| 4 | `Primitives.cpp` — `editValue` (numeric branch) | FIXED | Compared the raw target string (`"0x40"`) against on-screen text that only ever shows `"40"` — never matched even on genuine convergence. Fixed to parse both sides as hex and compare numerically. |
| 5 | `M8Device.cpp` — `ScreenGrid::cursorRowY()` | FIXED | The M8 skips redrawing a row's trailing blank cells when the cursor leaves it (a cyan space looks identical to a normal space), leaving stale cyan padding at the *vacated* row. The naive topmost-cyan-cell scan picked the ghost row over the real cursor's row. Fixed by requiring the picked cell be non-space. |
| 6 | `M8Device.cpp` — `M8Device::cursorField()` X-lookup | FIXED | Sibling bug to #5, not caught by the same fix: moving between two fields *on the same row* (e.g. EFFECTS' "MOD TYPE" → "INPUT EQ") left ghost cyan blanks at the vacated field's leading columns, and the X-position lookup picked the leftmost ghost instead of the real field. |
| 7 | `Primitives.cpp` — `moveCursorTo` (row-match branch) | FIXED | Always pressed RIGHT when on the correct row but wrong field. Real M8 multi-column rows (e.g. Sampler's SLICE/AMP pair) aren't reached column-by-column via UP/DOWN — DOWN from a full-width row (SAMPLE) lands directly on the row's *right*-column field (AMP), skipping the left-column field (SLICE) entirely. Fixed to compare target column vs. current column and press LEFT or RIGHT accordingly. |
| 8 | `ScreenModel.h` — `findScreenForField` | FIXED | Resolved short field names to the wrong screen via fuzzy substring matching — `"MST_CHO"` (Mixer) substring-matches `"CHO"` (Instrument/Sampler's chorus send), and since INSTRUMENT is checked before MIXER in the screen table, `"MST_CHO"` resolved to INSTRUMENT. Fixed to require an exact match across every screen first, falling back to fuzzy matching only if none exists. |
| 9 | `ScreenModel.h` — `kEffectsFields` | DATA | Every row was off by exactly one, with the wrong column (0 instead of 8). Root cause: the map was missing the CHORUS section's first row ("MOD TYPE"), so every field inherited a +1 offset — which "worked" by accident until the offset crossed the blank gap between the CHORUS and DELAY sections, at which point `DEL_EQ` became permanently unreachable. Re-measured all 14 rows/columns from pixel data. |
| 10 | `Primitives.cpp` — `moveCursorTo` (stuck-axis fallback) | FIXED | The row/column axis-fallback (added alongside #7) misfired on 1-pixel column measurement noise (e.g. `SYSTEM`'s label measures at col 1 even though its map entry says col 0), sending it into a useless LEFT/RIGHT loop instead of just continuing to press DOWN. Fixed with a >1-column tolerance. |
| 11 | `ScreenModel.h` — `kScaleFields` | DATA | `LOAD`/`SAVE` columns were wrong (0 and 5 instead of the real 7 and 12). |
| 12 | `Primitives.cpp` — `moveCursorTo` (stuck-axis fallback, latching) | FIXED | The axis-fallback from #10 was latched — once triggered it kept pressing LEFT/RIGHT forever, which could walk off the edge of a row's own sub-fields (SCALE's per-note EN/OFFSET columns) and then loop forever once that axis also stopped making progress, without ever giving the vertical direction another chance. Fixed to alternate (vertical, horizontal, vertical, ...) rather than latch. |
| 13 | `Primitives.cpp` — `readCursorValue` | FIXED | Never actually stripped the field's label from `cursorMainText()` despite its own doc comment claiming it did. On multi-column rows (e.g. `"AMP" + "FF"` → `"AMPFF"`), `editValue`'s numeric convergence check parsed the *leading* hex run — since `'A'` is a valid hex digit as well as a letter, it silently read "10" instead of "255" and could never match any real target, running all 256 steps and clamping at `0xFF`. Fixed by looking up the field's exact label from the field maps and stripping precisely that (a generic "skip leading letters" heuristic fails too — hex letters A-F are also alphabetic, e.g. `"TIMBRE"` ends in `E`). |
| 14 | `Primitives.cpp` — `editValue` (numeric stepping direction) | FIXED | The stepping loop only ever pressed `value_inc`, never `value_dec`. Values clamp at `0xFF` rather than wrapping, so a target below the current value was structurally unreachable. Fixed to pick direction from the parsed current-vs-target comparison each iteration. |
| 15 | `Primitives.cpp` — `loadFile` (climb to PROJECT) | FIXED | Used a separate, ad-hoc "press SHIFT+UP up to 8 times" loop instead of the already-hardened `gotoScreen`, duplicating a working mechanism with a less reliable one. SHIFT+UP from INSTRUMENT could land on INST_POOL instead of climbing toward PROJECT, with no way to recover (`rc=10`). Fixed by calling `gotoScreen(dev, Screen::PROJECT, ...)` directly. |
| 16 | `Primitives.cpp` — `loadFile` (file-selection scroll direction) | FIXED | The file-selection loop only knew how to scroll DOWN toward a target once it had scrolled out of the decoded viewport — a target *above* the current cursor position in the LOAD PROJECT browser (e.g. the first file in the list, browser left scrolled near the bottom from a prior manual browse) could never be reached (`rc=14`). Fixed by scrolling to the top of the list before searching. |
| 17 | `ScreenModel.h` — `kProjectFields` (`SAMPLEROOT`) | DATA | Field never existed on this firmware. Exhaustive search (SYSTEM SETTINGS submenu, MIDI settings submenu, LOAD PROJECT browser's OPT-key behavior) found no reachable field matching it anywhere; DOWN from `SYSTEM` (the real last row) never advances or scrolls, tested with both a tap and a 400ms hold. Removed the phantom field entry. Notably, this project's own SDL3 UI clone models `SAMPLE_ROOT` as a normal reachable field — a clone-vs-hardware discrepancy, flagged separately, out of driver scope. |
| 18 | `Primitives.cpp` — MIXER chain-walk (`isMixerChainField`) | FIXED, then REVERTED with the feature | Included `"IN_VOL"` in the recognized set, so the chain walker's own call to reach its entry point (`moveCursorTo(dev, "IN_VOL", ...)`) redirected straight back into the chain walker — infinite recursion. A single `cursor MIX_VOL` call hung 30+ seconds before being killed. |
| 19 | `Primitives.cpp` — MIXER chain-walk (hop retry) | FIXED, then REVERTED with the feature | On a hop mismatch, retried by pressing the *same key again* rather than just waiting longer. If the first press had actually succeeded but the read caught a stale frame, the second press advanced a second logical step — directly reproduced landing 2 fields past the intended target after 3 "failed" attempts that had each actually moved the cursor. |
| 20 | MIXER compound widget navigation (`MST_CHO`/`MST_DEL`/`MST_REV`/`MIX_VOL`/`LIM_VAL`/`DJF_FREQ`/`DJF_RES`) | **OPEN — but the central evidence did not reproduce; see the 2026-08-14 note at the end of this entry** | Root-caused, not fixable with a fixed key sequence: this widget's navigation is not a pure function of (current field, key pressed) — it depends on hidden state (most likely a per-column-group "last selected index" the M8 remembers independently of the visible cursor). Proven directly: a fully-isolated, hop-by-hop-verified path (`IN_VOL --RIGHT--> USB_VOL --RIGHT--> MIX_VOL --RIGHT-->...`) reproduced a *different* result on identical re-test after bugs #18/#19 were fixed. A fixed-sequence implementation was built, then deliberately reverted rather than shipped unpredictable. Also confirmed: the M8 remembers per-screen cursor position across screen re-entry, so a "bounce out and back" reset does not help escape this widget — only a bounded run of plain UP presses reliably does. `DJF_TYP`'s on-device position could not be located at all. **RE-TEST 2026-08-14 (fw 6.5.2, COM3, `m8drv`):** the non-reproducibility claim **did not reproduce**. Two runs, each `goto MIXER` → `home` (so both start from `OUTPUT VOL`, controlling for the M8 remembering per-screen cursor position — the earlier re-test did not control for this) → `probe RIGHT --times 6`, produced **byte-identical** cursor sequences: `E0`(row 120) → `EQ`(160) → `MIX E0`(170) → `LIM 00`(180) → `DJF 80`(190) → no further movement. That path traverses **three of the eight fenced fields** (`MIX_VOL`, `LIM_VAL`, `DJF_FREQ`) deterministically. The sixth press not moving is RIGHT exhausted at the right edge, not unpredictability — `OTT` (`DJF_RES`) sits below `DJF` and needs DOWN. This matters because the original finding rested on hop-by-hop cursor *reads*, and three defects in exactly that were fixed the same day (#22/#23/#24); #24 in particular made positions go stale **within** a connection while reading correctly in any fresh process, which is precisely what "identical re-test, different result" looks like. **Still OPEN, but narrowed from eight fields to three, and re-characterised.** `cursor MIX_VOL` from a homed start now **succeeds** (landed on `MIX E0`, row 170), so it is unfenced. `cursor MST_CHO` still fails (`rc=7`, 40 steps exhausted). **Leading hypothesis (2026-08-14): the map points at the wrong MX/DE/RE.** `{"MST_CHO", "MX", 10, 16}` resolves to y=190 col 10 under this file's `y = (row+3)*10` convention, and `MX` text *is* there — but there are **two** MX/DE/RE groups on this screen. y=170 carries three values (`E0 E0 FF`) with `MX DE RE` **labels beneath them at y=180**, which is the master-send block; y=190–210 is a separate 3×2 block of `MX`/`DE`/`RE` × `INPUT`/`USB` send levels. The map appears to aim at the input-send block rather than the master sends, which would make this the same DATA class as #9/#11/#17 and straightforwardly fixable by re-measuring. An earlier revision of this note asserted the map was correct; that checked the coordinate arithmetic but not *which* `MX` it landed on. Traversal data, both from `OUTPUT VOL` after `home`: `probe RIGHT` walks rows 50 → 120 → 160(`EQ`) → 170(`MIX E0`) → 180(`LIM 00`) → 190(`DJF 80`); `probe DOWN` walks 50 → 120 → 170(`00`) → 180(`INPUT`) → stop. The two agree on rows 170/180 but report *different fields* there, so they traverse different columns — which cannot be resolved from field names alone. With `cursor_col` added, the traversal resolves: RIGHT walks (row,col) 120,176 → 160,224 → 170,192 → 180,192 → 190,192; DOWN walks 120,104 → 170,104 → 180,104. **Neither ever reaches col ≤ 64 (cells 0–8) on row 170**, which is where the master-send values `E0 E0 FF` sit. So those three are not reachable from `OUTPUT VOL` by RIGHT or DOWN; LEFT or UP from elsewhere would have to be mapped. **CLOSED AS WON'T-FIX for now (2026-08-14), deliberately, not by oversight:** this is three fields on one screen, the neighbouring input/USB mixer is documented in `status.md` as never going to be implemented, and `MST_CHO`/`MST_DEL`/`MST_REV` are editable in the clone's own UI — driving them *on hardware* buys only parity-rig convenience. The fence keeps them from wasting an agent's time, `--unfence` exists for anyone who wants to try, and the traversal data above means the next attempt starts from measurements rather than from scratch. Reopen if on-device authoring of master sends ever actually matters. |

| 22 | `M8Device.cpp` — `ScreenGrid::cursorRowY()` | FIXED | Reported the **column-header row** as the cursor row on grid screens, so `cursor_row`/`cursor_field` never advance there and `moveCursorToGrid` cannot converge. This is the second half of #3 ("a naive color scan (no row floor) could pick up the column-header label instead of the real cursor"), which was fixed in `moveCursorToGrid` but never in `cursorRowY()` itself. Evidence (2026-08-14, fw 6.5.2, COM3, via `m8drv probe`/`goto`): on SONG, `cursor_field` reports `"1"` at `cursor_row: 50`, and y=50 is the **track-number header** (`1 2 3 4 5 6 7 8`) — the first data row is y=60 (`00 00 -- ...`). Three DOWN presses at `hold_ms: 40` left it pinned at 50 with `baseline_drift: 0`, and `cursor-grid 4 2` failed `rc=7`. PROJECT is unaffected (cursor tracks 50→60→70→80 through TRANSPOSE/GROOVE/SCALE) because its cursor is accent-coloured *text*, which the scan is built for. **Root cause, measured (`m8drv inspect --key DOWN`, fw 6.5.2, COM3, 2026-08-14):** accent-foreground cells sat at `(row 5, col 19) = "6"` — the *column*-header indicator showing which track column the cursor is on — and at `(row 11, cols 1-2) = "05"` plus `(row 11, cols 19-20) = "--"`, the cursor's own row. One DOWN press moved the latter to `(row 12, cols 1-2) = "06"` and left the header indicator untouched. So the presses were landing, the cursor *was* accent-foreground and detectable all along, and the sole defect was that `cursorRowY()` took the **topmost** accent cell — which on a grid screen is always the header, because the header sits above the data and tracks the cursor too. `rect_count` was 0 and no accent-background cell existed, ruling out both the rect-fill and inverse-video theories. **Fix:** prefer an accent (or `'<'`) marker in the left label columns (`x < 24`) before falling back to the generic scan; the M8 recolours the cursor row's own leading row-number, which is unambiguous. Tests: `cursorRowY prefers the row label over the column header` and `cursorRowY still finds a form-screen cursor label` (`[hwdecode]`). The same run also confirmed bug #5's ghost mechanism live on hardware — `(row 11, col 3, ' ')` survived the press that moved the cursor — so the `ch != ' '` guard is load-bearing in both branches. **Superseded notes:** an earlier revision of this entry blamed the `ch == 0x3C` (`<`) branch (wrong — SONG displays no `<` at all), and a later one blamed a rect-fill/inverse-video cursor (wrong — neither exists on this screen). |

| 23 | `Primitives.cpp` — `moveCursorToGrid` column handling | FIXED | Every call failed `rc=7` ("could not reach step N col M") on grid screens, because the column half was wrong in three independent ways that compounded. (a) `detectColPitch()` returned the smallest gap between any two non-space cells anywhere on screen — 8px, the pitch of adjacent glyphs *inside* one cell — not the 24px pitch between SONG's track columns. (b) Column 0's X was calibrated from wherever the cursor currently was, so the current column always computed as 0. (c) `findCursorCell()` returns the **leftmost** accent cell on the cursor's row, which is the row-number label; its X does not change when the cursor moves sideways, so the column reading was pinned regardless. Net effect: with pitch 8, "col 2" meant 16px right of the cursor — *inside* the current cell, a position RIGHT (a full 24px hop) can never land on — so the loop oscillated 0→3→0→3 until `maxSteps` ran out. Confirmed on hardware after bug #22 was fixed: `probe DOWN` tracked rows 120→130→140→150 correctly while `cursor-grid 4 2` still failed, isolating the defect to the column axis alone. **Fix:** derive column edges from the column-header row (each run of consecutive non-space header cells is one column, and its start X is that column's left edge), and read the current column from the accent-highlighted header cell — the M8 highlights the header cell of the column the cursor is on, which is a direct readout rather than a measurement (confirmed fw 6.5.2: the track-6 header digit was accent-coloured while the cursor sat in track 6). Falls back to the rightmost accent cell on the cursor's row when no header cell is accented, since header highlighting is verified on SONG only. `targetCol` is now range-checked against the actual column count instead of failing opaquely. `detectColPitch()` deleted — it had no other caller. |

| 24 | `Primitives.cpp` — `findCursorCell` | FIXED | Missing the `c.ch != ' '` guard, so it latched onto the accent-coloured **blank** the M8 leaves at a vacated row and reported the OLD row indefinitely. Third site of the #5/#6 ghost family: `ScreenGrid::cursorRowY()` got the guard (#5), `M8Device::cursorField()`'s X-lookup got it (#6), and this one never did — despite being what every grid-screen position read goes through. **Why it stayed hidden until now:** `open()` sends `'R'`, a full-framebuffer resend that repaints ghosts away, so any *one-shot* `m8_nav` invocation reads correctly. The bug only appears on the second and later reads **within one connection** — i.e. it was invisible until the driver stopped spawning a process per command. Evidence (fw 6.5.2, COM3, 2026-08-14, `m8drv probe DOWN --times 3`): `cursor_row` advanced 150→160→170 across three presses while `grid_step` stayed pinned at `8`, the value from before the first press; a following `probe RIGHT` in a fresh process read `grid_step` as `11` (correct for row 170) and tracked `grid_col` 3→4→5 cleanly. This is also why `cursor-grid 7 5` failed while `cursor-grid 4 2` had succeeded — the latter ran right after an `'R'` with no ghosts yet and its start step already read 4, whereas the former needed vertical movement, whose progress the pinned read hid, so it pressed DOWN to the bottom and gave up on the no-progress counter. | 25 | `Primitives.cpp` — `editValue` numeric stepping | FIXED | Single-stepped the value, up to 256 presses, each carrying a `readSettled(120, 200, 1200)`. At that ~320ms floor one byte edit costs over a minute and the worst case (0xFF→0x40) more than four, so `m8_nav --script tests/hw/set_param.m8script` presents as a hang rather than as slow work — reported 2026-08-14. Not merely an optimisation: it made `set` unusable in any interactive or scripted loop. `hw_buttons.json` had pinned `value_inc16`/`value_dec16` (EDIT+UP / EDIT+DOWN, a nibble step) since 2026-07-17, and `editValue` never used them. **Fix:** coarse-step while the remaining gap is at least one coarse step, then fine-step, which bounds a byte edit at roughly 30 iterations instead of 255. The coarse step's size is **measured at runtime**, not assumed: one probe press is issued and the observed delta recorded, because "nibble/octave increment" is a hex-shaped description with no guarantee of landing on 16 for every field type (a decimal field such as TEMPO need not behave like a hex byte), and a field where the gesture does nothing falls back to fine steps rather than stalling. Clamping at 0x00/0xFF needs no special case — the value is re-read every iteration, so a clamped step simply shows up as a smaller gap. |

| 26 | `Primitives.cpp` — `editValue` target parsing | FIXED | Parsed the **target** with `strtol(..., 0)` (bare digits = decimal) while parsing the **screen text** as base 16, so the two sides were read in different bases. `set PAN 80` therefore converged — correctly and silently — on 80 decimal = `0x50`, and the device showed `50`. Reported 2026-08-14 while setting up a stereo measurement; the earlier `set` runs all happened to be unambiguous (`0x40`/`0xC0` explicit, `02` identical in both bases), which is why it had not surfaced. Silent wrongness is the worst failure mode for an agent-driven tool: nothing in the result said anything was off. **Fix:** parse the target as base 16, matching both the device's display and the existing screen-side parse; `strtol` with base 16 still accepts an explicit `0x` prefix, so previous callers are unaffected. Does **not** regress TEMPO-style decimal fields, which were already unreachable — `readCursorValue` yields `"120.00"` whose leading hex run parses as `0x120` = 288, so no decimal target could ever match. Editing decimal fields needs a per-field base and is not attempted here. |

An unmapped stop now yields *no name* rather than a wrong one, so `moveCursorTo` keeps navigating instead of declaring victory. Tests: `identifyCursorField refuses a distant field` (`[hwdecode]`).
| 32 | `M8Device.cpp` — frame decode has no validation | OPEN | A desynchronised serial stream renders as a **plausible but wrong screen**, and every layer above believes it. Observed 2026-08-18 (fw 6.5.2, COM3): an INSTRUMENT capture whose rows 3-5 were perfect and whose rows 6+ drifted cumulatively -- NAME's value one row low and eight columns left, `TRANSP.` wrapping mid-word across two rows, the left column reappearing at column 31. Absolute positioning cannot produce a wrapped word, so the x/y fields were being read at the wrong byte offsets: one lost or extra byte shifts every subsequent field boundary. **Nothing detects it.** `0xFD` requires `f.size() >= 12` and silently `return`s otherwise; decoded x/y are written straight into `cells[{y,x}]` with no bounds check, so coordinates outside the 320x240 panel or off the 8x10 pitch are accepted as readily as valid ones. `--ui-capture`'s settle check compares only `topHeader()`, which sat in the undamaged rows and matched twice, so the capture was written with `settled: true`. **Downstream symptoms this produced, all misleading:** `read PAN` -> `field not found: PAN` (the label was not where the grid said), and `set TYPE` -> `could not find enum ... from TYPE    LOAD`, which reads as a navigation bug and is not one. **Suggested fix:** reject a `0xFD` whose x/y fall outside the panel or off-pitch, count rejects, and surface a non-zero reject count as an explicit unreliable-read error rather than returning a grid. A short-form `0xFD` (the compact variant m8c handles, reusing the previous colour) being dropped by the `size() >= 12` guard is a second candidate cause worth checking against a frame dump -- `m8_nav --record-frames` exists for exactly that. Not yet reproduced deliberately.
